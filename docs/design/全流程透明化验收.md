## 六、2026-09-21 追加：伏笔编码分配根因修复（用户截图触发排查）

- **现象**：digest 提议连续撞 `uq_foreshadows_novel_code` 被 WARN 跳过——看似幂等无害，实为**静默数据丢失**。
- **根因**：`nextCode` SQL 返回裸数字「当前最大值」（无 F 前缀、无 +1），且正则 `^F[0-9]+$` 把 ch62 时代误插的脏行 `code='72'`（无前缀）排除在 MAX 之外——此后每次 digest 都拿到 72、插 `72`、撞脏行、跳过。**ch62 起 digest 的全部新伏笔提议被丢弃**。
- **修复**：`nextCode` 改为 `'F' || (MAX+1)`，MAX 用 `REGEXP_MATCH(code,'^(F)?([0-9]+)$')` 兼容裸数字行；实测下一编码 F77。
- **数据修复**：脏行 `'72'`→`F73`；从 llm_call_log（id 618/628 的 digest 响应）找回被丢的 3 条提议落库 F74-F76（银痕的时间悖论@63、樟脑味锚定前主人学院底层@64、三墨三手时序与情感递减@64）——**台账全量留档再次成为数据恢复的兜底**。
- **附带**：SSE 客户端断开后的迟到写失败（SocketTimeoutException）不再以 ERROR 级进全局处理器（响应已提交，静默忽略）。
- **教训入册**：catch+跳过把「崩溃」变「静默丢数据」比崩溃更危险——吞异常的分支必须同时上报可观测信号（本例 WARN 有留痕才得以发现，但丢失本身无告警；后续 digest 新增「提议 N 条中 M 条被跳过」的显式事件）。
