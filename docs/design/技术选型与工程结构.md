# 技术选型与工程结构（MVP）

> 前置文档：`docs/design/系统架构设计.md`（五层架构，本文档负责"用什么实现它"）
> 目标：达到《咱家是猫，在观察人类》级别的稳定续写，**100 万字以上**长跑；只做 MVP。

## 一、结论

| 项 | 选型 | 一句话理由 |
|---|---|---|
| 语言 | **Java 21**（开虚拟线程） | 你最熟；负载画像里没有一项需要换语言 |
| 框架 | **Spring Boot 3.5.x** | 依赖注入/配置/事务/CLI 都是现成的 |
| AI 层 | **MVP：自写 `LlmPort` 接口 + `MiniMaxClient`（RestClient + Jackson）；Spring AI 1.x 推迟到 M4 作 adapter** | 薄客户端可控、可全量落盘重放；结构化输出/向量检索需求出现时再引入 |
| 存储 | **PostgreSQL 16 + pgvector** | 架构文档 §8.1 已定；一个库装下结构化表和向量 |
| ORM | Spring Data JPA + Flyway | 结构化表 + 版本化迁移；不用引入 MyBatis 除非你更顺手 |
| 向量检索 | Spring AI PgVectorStore | 范例段/语气样本的语义召回开箱即用 |
| 形态 | **单模块 Maven 单体 + Web 多租户（MVP 仅 admin 账号）** | 用户平台定位见《MVP共识与决策记录》；CLI 仅留 ingest 等运维命令 |

**明确不引入**（MVP 阶段）：

- **Python / LangChain**：本系统**没有本地模型推理、没有训练、没有数据科学**——AI 部分全部是 API 调用 + 编排 + 持久化。Python 生态的优势（本地跑模型、notebook 实验）一项都用不上，而你的交付速度会掉一半。
- **Go**：同理，语法熟练度不足以覆盖 MVP 的迭代速度需求。
- **Temporal / Camunda / Kafka**：这是"100 个节点、跨机重试、多团队"时的工具。MVP 的流程是**一条 10 节点的状态机**，一张 `chapter` 表的 status 字段 + 幂等步骤 + 落盘中间产物就够了（见 §四）。重试、恢复、审计全都有，没有分布式协调问题。
- **微服务**：单进程。拆服务的唯一结果是让"为什么这章跑偏了"更难排查。
- **独立向量库（Milvus/Qdrant）**：百万字 ≈ 几千个向量，pgvector + HNSW 索引绰绰有余，少运维一个组件。
- **LangChain4j**：功能与 Spring AI 重叠，你熟 Spring 生态，没有理由混用。

## 二、为什么 Java 完全扛得住"100 万字"

先看负载画像——这个系统的瓶颈排序：

1. **LLM API 的吞吐与费用**（一章 1.5–2K 字要几十次调用：草稿+评审+修订循环）——语言无关
2. **流程编排与状态管理**（哪个章在什么状态、哪轮修订失败）——Spring 事务/JPA 的舒适区
3. **文本持久化与检索**（百万字入库、digest 链、向量召回）——Postgres 的舒适区
4. **机械门禁**（正则、字数统计、指标区间）——JVM 正则/流式处理毫秒级

Java 唯一"重"的地方是启动慢和样板代码，而这是一个**长跑批处理系统**：进程一跑几小时，启动 3 秒还是 0.3 秒毫无意义。100 万字 ≈ 60 万 token 量级的存量文本，对 Postgres 来说是小表；真正的伸缩压力永远在 MiniMax 那一端，语言帮不上也拖不后腿。

## 三、Spring AI 能力 → 架构节点映射

| 架构节点（§三） | Spring AI 实现 |
|---|---|
| 章纲生成 | `ChatClient` + **结构化输出**（`entity(ChapterOutline.class)` 直接映射成 record，拒绝自由文本解析） |
| 场景草稿 | `ChatClient` + prompt template（`PromptTemplate` 渲染上下文包），输出纯文本 |
| AI 评审 | 结构化输出 → `ReviewReport` record（四维 rubric、行号证据、pass/fail） |
| 修订 agent | MVP 用**程序化循环**（收门禁报告→重写→重跑门禁，≤3 轮）；Spring AI 的 tool calling 留给检索 agent |
| 检索 agent（v2） | Spring AI tool calling：给模型 `searchCanon()` / `searchExemplars()` 工具 |
| Embedding | `EmbeddingModel` 接口；MiniMax embedding 接进去（见 §五） |
| 范例召回 | `PgVectorStore`（similarity search，按场景类型过滤 metadata） |
| 每节点不同温度/超时 | 每个节点独立 `ChatClient` bean，各配 `OpenAiChatOptions` |

接入 MiniMax：它的 API 兼容 OpenAI 协议，**用 Spring AI 的 OpenAI starter 改 `base-url` 指向 MiniMax 即可**（`spring.ai.openai.base-url` + api-key 走环境变量）。chat 直接可用；embedding 若兼容接口不可用，自己实现一个 `EmbeddingModel` 适配官方 HTTP 接口，半天工作量。不把 key 写进任何提交文件。

## 四、流程控制：状态机而不是工作流引擎

`chapter` 表一行 = 一章的生命周期，所有步骤幂等、产物落盘（架构文档 §八的原则）：

```
OUTLINED → DRAFTING → GATE_MECHANICAL → GATE_AI_REVIEW
   → (REVISING ×n) → FINAL → DIGESTED → INDEXED
   任何一步失败：status 停在原地 + reports/ 留下完整现场，重跑命令从断点继续
```

实现就是一个 `ChapterStateMachine` service：每个状态对应一个幂等方法，`UPDATE ... WHERE status = 前置状态` 抢占式推进。并发生成多章时用**虚拟线程**（Java 21）扇出，省掉消息队列。将来真长成多机系统了，这张状态表就是迁移到 Temporal 的现成规格说明，一点不浪费。

## 五、工程结构（单模块 Maven）

```
zzdzz-novel-generate-mvp/
  src/main/java/zzdzz/novel/
    llm/            # ChatClient beans、各节点 prompt 常量、MiniMax 适配
    canon/          # 资产层：人设卡/世界规则/伏笔账本 实体+仓库+导入器
    outline/        # 规划层：卷纲/章纲生成（结构化输出）
    generate/       # 生成层：上下文打包器、场景生成、拼章
    gate/           # 门禁层：MechanicalGate(纯Java)、AiReviewer、RevisionLoop
    state/          # 状态层：digest 生成、角色状态、伏笔账本、章节状态机
    infra/          # PgVector 配置、Flyway、CLI 命令
  src/main/resources/
    db/migration/   # Flyway DDL
    prompts/        # 各节点 prompt 模板文件（热改不重编译）
```

关键表（对应架构 §四数据模型）：`chapter`（含 status）、`chapter_outline`、`scene_draft`、`gate_report`、`digest`、`character_card`、`character_state`、`foreshadow`、`style_rule`（规则表）、`exemplar`（含 vector 列）。

CLI 命令（Spring Shell 或裸 `CommandLineRunner`，MVP 够用）：

```bash
novel ingest          # 冷启动：导入手搓两章 → 生成 digest/人设卡草稿
novel outline --ch 3  # 生成章纲（人批后 outline approve）
novel write  --ch 3   # 跑完整管线：草稿→门禁→修订→digest
novel retry  --ch 3   # 从失败断点续跑
```

## 六、MVP 开发顺序（对齐架构里程碑）

1. **骨架周**：Boot 工程 + Flyway 建表 + OpenAI-starter 接 MiniMax（先跑通"给我吐 500 字"）
2. **M1 单章直通**：ingest → outline → 上下文打包 → 场景生成 → 拼章 → MechanicalGate（纯 Java 正则门禁先上线，它零成本且立刻能拦 AI 腔）
3. **M2 评审闭环**：AiReviewer 结构化输出 + RevisionLoop 程序化循环
4. **M3 记忆续写**：digest 链 + character_state 推进 + 断点重跑
5. **M4 风格回归**：exemplar 入 pgvector + 范例语义召回 + style_rule 表驱动门禁 + 指标监控

每一步的验收标准都在架构文档 §九，不重复。
