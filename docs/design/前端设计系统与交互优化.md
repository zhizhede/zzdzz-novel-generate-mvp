> 分支：`10/1003-前端设计系统与交互优化`（从 `10/1003-命名回退与口径修正` @ `0b6fe91` 切出，沿用整条未合并链）
> 制定日期：2026-10-03

## 一、背景与判断

前端骨架（Vue3 + Element Plus + 路由 + fetch 封装）是合理的，问题不在选型，而在**缺一层设计系统**，导致所有细节问题被放大：颜色与字号全靠手写常量，「改一处」永远是改两百处。

本方案的目标不是「换一套皮」，而是补上这层地基，让后续每次 UI 调整都变便宜，并顺带补上两块产品本位欠账（长文本阅读面、导航可发现性）。

### 已实证的排版缺陷（2026-10-03 用户截图，规划页卷纲表）

`PlanningView.vue:52` 的表声明了列宽却同时压了上限，两者自相矛盾：

```
定宽列：章 60 + 标题 160 + 时间跨度 130 + 状态 130 + 操作 220 = 700px
弹性列：目标 min-width 220 + 钩子 min-width 200            = 420px
声明列宽合计 = 1120px    ←→    容器 style="max-width: 980px"
```

后果三连（同一根因）：① 列被压扁，`时间跨度` 名义 130px 实际约 40px，表头**竖排成 4 行**；② 末列「操作」被裁在表格右边缘；③ 1920 窗口下约 **43% 宽度全空**。这不是「留白不好看」，是宽度上限与列宽声明打架——**本方案据此把「表格宽度口径」升格为跨阶段的全站规则**（见第三节）。

### 做得好的部分（本方案保留，不重做）

- 会话视图（`WorkbenchView.vue` 的 `pstream`/`scene` 转录块）——分阶段标签、字数计、tokens、节奏读数、思考折叠，这套 agent-IDE 式实时转录是本产品最好的交互资产。
- `api.js` 的 `CODE_HINTS` 错误码人话层、`main.js` 的全局 `errorHandler`。
- 各页已有的 `el-empty` 空态（13 处）。

## 二、范围

**做**：表格宽度口径（P2，跨阶段全站规则）、设计令牌层（P1）、布局原语（P3）、散点归并（P4）、正文阅读面（P5）、素材库拆分（P6）、侧栏导航分组（P7）、加载态与键盘可达（P8）。

**不做**（明确排除，避免范围膨胀）：

1. 不改任何后端接口、DTO/VO 字段、契约文档。
2. 不改任何业务逻辑与请求时序。
3. 不做全站响应式重写（仅在 P3 给工作台双栏加一个最小断点，其余留给后续独立批次）。
4. 不做无障碍全面合规（P8 只做表格行点击的键盘可达，其余单独立项）。
5. 不按 `code-standards.md` §2 重排前端目录（`api/` `stores/` 等）——属「架构轮」范围，本项目已明示推迟。
6. 不动 Element Plus 版本，不引入新的 UI 依赖。

## 三、宽度口径：按比例，不设 px 上限（全站规则，P2 落地）

这条独立成节，是因为它跨所有页面、且优先级高于其余样式工作——它决定「页面看起来正不正常」。

**核心原则：宽度按容器比例分配，禁止裸 px 上限。** 本方案初稿曾提议把逐页 `max-width` 收成一个全局 `--ng-content-max: 1680px`——那只是把 18 个魔法值合并成 1 个魔法值，病根没除。正确做法是让宽度由容器比例决定。

**规则**：

1. **表格一律 `width: 100%`**，占满内容区，不设任何 px 上限——窗口多宽，表格多宽。彻底删掉逐页 `max-width`（清单见附录 B）。
2. **多余宽度按比例分给弹性列**：定宽列只用在真正定宽处（章号/状态/操作），其余列一律 `min-width`，由 Element Plus 按比例分配剩余宽度。窗口变宽时是**内容列变宽**，不是表格变宽。
3. **禁止「声明列宽合计 > 容器宽度」**：这是 `PlanningView.vue:52` 那个缺陷的根因，P2 逐表核销。
4. **表头不竖排**：表头 `white-space: nowrap` 并给列宽下限，杜绝 `时间跨度` 这类四字表头折成 4 行。
5. **确需上限时用比例或字号相对单位，不用 px**：优先 `min(100%, Nvw)`；与字号相关的用 `rem`/`em`/`ch`（随用户字号缩放）。若某处确实需要 px 硬上限，必须在附录 B 登记并写明理由（如 `LoginView.vue` 的登录卡 360px）。
6. **长文正文的上限用「全角字数」表达**（P5 阅读面）：`46em` 这类随字号缩放的版心，而不是 px——用户调大字号时版心同步变宽，每行仍是同样的字数。

**执行顺序**：先做 P2 的表格宽度（改动小、收益立刻可见、可独立回退），再让 P3 的 `DataTable` 组件把这条规则固化下来，避免全站表格被改两遍。

## 四、施工阶段

> 阶段顺序按「可见收益 / 风险」排：先落用户看得见的（表格宽度、令牌），再落结构性的（原语、拆分）。

### P1 设计令牌层与样式入口

**前置已完成**：设计本身已用 OpenDesign 产出，落地为 `web/design-system/`（见附录 C）。令牌源、映射层、契约散文都在那里，P1 只做「接线」，不再自行发明令牌。

- 新增 `web/src/styles/tokens.css` → `@import` 包的 `tokens.css`
- 新增 `web/src/styles/element-plus.css` → `@import` 包的 `element-plus.css`
- 新增 `web/src/styles/app.css` 应用壳层：给根元素上羊皮纸底、body 外边距归零。**必需而非可选**——Element Plus 不消费 `--el-bg-color-page`（产物里无选择器使用它）、布局容器透明，且本项目此前零全局样式（body 的 UA 默认 8px 外边距一直在），缺了它画布不变色、应用外留一圈白边
- 在 `main.js` 按 **Element Plus 自带样式 → tokens.css → element-plus.css → app.css** 的顺序引入（顺序反了会被默认值盖回）
- **令牌命名沿用 OpenDesign 契约的原名**（`--bg` / `--fg` / `--muted` / `--meta` / `--accent` / `--text-sm` …），**不另加 `--ng-` 前缀**：这样包能作为合规的 OpenDesign 设计系统被上游工具直接读取。与 Element Plus 的 `--el-*` 无碰撞风险；若日后引入其他组件库产生裸名冲突，再统一加前缀并同步改包契约。
- **风险**：低（纯新增；但 `color-mix()` 需现代浏览器，本机 Chrome/Edge 满足）
- **证据**：`npm run build` 通过；`npm run dev` 转译通过（dev 才是用户实际入口）；产物中可 grep 到令牌；契约完整性/语法/对比度三项机械核验已过（附录 C）

### P2 表格宽度口径全站落地

- 按第三节规则 1/2/3/4 逐表处理：删掉 `max-width`、把弹性列改 `min-width`、补齐表头 nowrap
- 重点先修已实证的 `PlanningView.vue:52`（1120 vs 980 矛盾）
- 无 px 版心可加：表格直接吃满 `el-main` 的内容区
- **风险**：低（纯样式，但涉及 18 张表 + 8 处非表格容器，共 26 个 `max-width` 声明）
- **证据**：改前改后逐表核对「声明列宽合计 ≤ 容器宽度」；`npm run dev` 打开规划页/素材库/规划资产逐页确认；**用户目检**（见第六节检查点 A）
- **回退**：单 commit 可整体 revert

### P3 抽取布局原语

- 新增 `web/src/components/PageHeader.vue`：标题 + 副标题 + 操作区 slot，消掉各页重复的 `display:flex; align-items:center; gap:14px; margin-bottom:6px`
- 新增 `web/src/components/DataTable.vue`：包装 `el-table`，把第三节的口径固化进去（满宽、统一 `border`/`size`/`loading`/`empty`、表头 nowrap、列宽校验）
- 先在 `ChaptersView.vue` + `BooksView.vue` 试点验证，**不一次性推全站**；工作台双栏同时收一个最小断点（窄窗改单列）
- **风险**：中（动模板结构，可能影响插槽透传）
- **证据**：试点两页 `npm run dev` 打开确认；`el-table-column` 插槽全量透传（逐列核对模板读到的字段）；行数变化对表

### P4 归并散落的灰阶与字号为语义令牌

- 先出一张映射表（写入本文档附录），逐条判定 7 种灰各属哪一级语义，**不做机械替换**——`#999` 有 134 处，需区分「次要说明文字」与「禁用/占位」
- 替换全部硬编码六位灰与 px 字号为令牌引用
- **改法**：逐文件走 Edit 工具；**禁止 python/heredoc 打补丁**（`AGENTS.md` 坑 1：Git Bash heredoc 吃反斜杠）
- **风险**：中低（纯样式，但 222+190 处量大）
- **证据**：改前后 grep 计数对表（`#999` 残留数应降至 0，仅令牌定义处除外）；`npm run build` + dev 转译；引用 grep 确认无遗留硬编码

### P5 正文阅读面

- 新增 `web/src/components/ReadingPane.vue`，替代目前章节抽屉里裸的 `white-space: pre-wrap; line-height: 1.9`
- 提供：字号（16/17/18/20）、行高（1.6/1.8/2.0）、版心宽度（32–52 全角字/行，**实现为 `em` 而非 px**，见第三节规则 6）、衬线/无衬线切换、主题（浅/深/护眼米黄）
- 补中文排版惯例：**段落首行缩进 2 字符**、段间距独立于行高（当前完全没有，长文阅读体验的最大短板）
- 设置持久化 `localStorage`
- 同时应用到会话视图的正文块
- **风险**：中（新增交互，涉及持久化与现有 drawer 结构）
- **证据**：dev 打开实读一段真实章节；字号/行高/版心切换逐档确认；localStorage 键名与恢复逻辑核对

### P6 素材库按域拆分

- `LibraryView.vue` 的 23 个 tab-pane 按域抽成 `web/src/views/library/*.vue` 面板组件，`LibraryView.vue` 只留 tab 壳与共享加载逻辑
- 这是「拆巨类」的**局部轻量版**：不改路由、不改接口、不引入 store、不做目录重排
- 建议**先抽最大的 3 个 tab**（素材卡 / 伏笔账本 / 模型接入）验证插槽与 props 传递，稳定后再推其余
- **风险**：中高（1770 行搬运，易漏 `v-model` 与 emit）——本批唯一需要放最后做的阶段
- **证据**：每个 tab 逐个 dev 打开；按 §2 原子性每域可独立回退；拆分前后 `el-tab-pane` 数量对表

### P7 侧栏导航分组（需确认）

- 现在 9 项平铺，且「平台配置」「模型接入」藏在侧栏标签叫「素材库」的页面里，用户猜不到
- 建议按域分组：生成（工作台/开新书）· 内容（书籍管理/章节/规划/规划资产）· 资产（素材库/文风指纹）· 系统（调用台账）
- 配套：把 P6 拆出的「平台配置/模型接入」提升为独立路由或素材库下的二级菜单
- **风险**：中（改导航即改用户肌肉记忆）
- **待决**：是否接受导航结构调整（见第八节）

### P8 加载态与键盘可达

- **证据**：dev 打开逐页确认；键盘 Tab/Enter 实按一次

## 六、验证策略（本方案的关键约束）

**本项目的视觉走查有两道独立障碍**：用户全局规则禁用可见浏览器面板，且本机 `agent.browsers.list()` 只返回 `iab` 一个后端（无 headless 可用）。因此**本方案不承诺视觉走查**，改用替代证据顶住，并显式列出未覆盖面。

替代证据五件套（每个阶段收尾执行）：

1. **dev 转译** `npm run dev` 通过（用户实际入口是 dev server，不是 `dist`）
2. **生产构建** `npm run build` 通过（抓模板语法/引用错误，可查新组件是否独立成 chunk）
3. **字段契约核对**：模板真正读到的字段与接口返回做双向差集（本批不改接口，预期差集为空——作为「没改坏」的证伪）
4. **引用 grep**：换掉旧写法后确认无残留（如 `max-width` 逐页魔法值应降至 0；`#999` 归并后全站残留数）
5. **接口实弹**：后端 8090 起，登录后跑一遍涉及页面的读接口

**必须显式声明的未覆盖面**（对人眼才可见的，直接请用户点）：

- 视觉观感（颜色/间距/宽度是否真的更好看）
- 动效过渡是否自然
- 阅读面的字号/行高切换手感
- 拖拽手势（本轮不涉及）

**用户目检检查点（3 处，不可省）**：

- **检查点 A（P1 接线完成后）**：全站**一次性换色**——`--el-*` 被整体重映射，所有表格、标签、按钮、对话框的颜色和次要文字色同时变化。这是本批最大的一次视觉变化，必须人眼过一遍：打开 2–3 页确认「只是变规范了，没有变样/变坏」，尤其是暖羊皮纸底在真实数据量下会不会显得旧、墨蓝作主色够不够清楚。**这一关不过就不要继续往下做。**
- **检查点 B（P2 完成后）**：用户打开规划页/素材库/规划资产，确认表格已满宽、表头不再竖排、末列不再被裁。这是用户已实际报告过的问题，必须闭环确认。
- **检查点 C（P6 完成后）**：用户逐个 tab 点一遍素材库 23 个页签，确认拆分没漏功能。这是本批风险最高的阶段，必须人工过。

后端配合：本轮为纯前端，除 P5 实读需后端在跑外，无需重启规避（`mvn clean` 会删运行中后端的 `target/classes`，见 `AGENTS.md` 坑 5）。

## 七、风险与回退

| 风险 | 应对 |
|---|---|
| 表格改满宽后长行难读（列被拉得过开） | 定宽列不拉伸，多余宽度按比例分给 `min-width` 弹性列（规则 2）；超宽屏是否设比例上限见第八节第 4 条 |

### P2 执行结果（2026-10-03，commit 4）

清理了 **18 张表的 `max-width`** 与 **4 处非表格容器**的上限。

**执行中发现的一条源码级事实（比 max-width 更根本）**：读 `element-plus/es/components/table/src/table-layout.mjs` 的 `updateColumnsWidth()`——

```js
const flexColumns = flattenColumns.filter((column) => !isNumber(column.width))
if (flexColumns.length > 0 && fit) { /* 把剩余宽度按 minWidth 比例分给弹性列 */ }
else { /* realWidth = width || minWidth；表格宽度 = 各列之和，不拉伸 */ }
```

即 **el-table 只在「存在弹性列（列上没有数字 width）」时才分配剩余宽度**。一个全列定宽的表，即使删掉 `max-width` 也照样按各列之和渲染，右侧仍留空——**光删上限治不了这类表**。

因此额外把 4 张全列定宽表中的描述列改成 `min-width`，使其成为弹性列（并把该检查脚本化：正则须写 `<el-table(?![-\w])`，否则 `<el-table\b` 会连 `<el-table-column` 一起匹配，我第一版就因此把 237 个列误报成表）：

| 表 | 原渲染宽度 | 处理 |
|---|---|---|
| `ChaptersView.vue:70` 门禁检查表 | 580px | 指标列改 `min-width` |
| `LibraryView.vue:72` 正典文档 | 440px | 名称列改 `min-width` |
| `LibraryView.vue:412` 指纹基线 | 520px | 指标列改 `min-width` |
| `LogsView.vue:32` 调用台账（11 列） | 1100px | 节点与模型列改 `min-width` |

**收尾核验**：全站 37 张表，**0 张全列定宽**；表格 `max-width` 残留 0；`npm run build` 通过。

**已知观感风险**：`LogsView` 的调用台账是 11 个窄列均质表，拉满到 1720px 后「节点/模型」两列会明显偏宽（节点名最长约 18 字符）。这是「按比例铺满」规则在均质窄列表上的固有代价，取舍留给人工检查点 B 判断。

## 附录 C：设计系统来源与产出（2026-10-03）

### 工具

用 [OpenDesign](https://github.com/nexu-io/open-design)（Apache-2.0，开源版 Claude Design 替代品）出设计。它不自带 agent——PATH 上的 coding agent 才是设计引擎；它提供的是可移植的 design systems / skills / templates / plugins 四类资产。本机安装于 `D:\Program\open-design`（只装了 design-systems 目录 + 契约 + 取用脚本，全量 277MB 未取；原因与本机 GitHub 通道说明见该目录 `INSTALL-NOTES.md`）。

### 基座选择

153 个设计系统里选 **`kami`（紙 / 纸，Editorial & Print）**作基座，理由：

1. 它是目录里唯一**从设计之初就为 zh-CN 排版**做的系统（带 TsangerJinKai02 / 思源宋体中文衬线栈，且明写支持 EN · zh-CN · ja）；
2. 印刷节奏（行高 1.45–1.55、标签用实色 hex、数字 `tabular-nums`）与数据表密度天然接近；
3. 暖羊皮纸底 + 墨蓝单一彩色，比 `claude`（赭石，偏消费向）更贴合「专业写作工具」而非「聊天产品」。

对照过 `claude`（暖羊皮纸/赭石/文学化）与 `linear-app`（暗色优先/高密度），二者未采用。
