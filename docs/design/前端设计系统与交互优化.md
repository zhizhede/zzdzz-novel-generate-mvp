## 一、背景与判断

前端骨架（Vue3 + Element Plus + 路由 + fetch 封装）是合理的，问题不在选型，而在**缺一层设计系统**，导致所有细节问题被放大：颜色与字号全靠手写常量，「改一处」永远是改两百处。

本方案的目标不是「换一套皮」，而是补上这层地基，让后续每次 UI 调整都变便宜，并顺带补上两块产品本位欠账（长文本阅读面、导航可发现性）。

### 已实证的排版缺陷（2026-10-03 用户截图，规划页卷纲表）

`PlanningView.vue:52` 的表声明了列宽却同时压了上限，两者自相矛盾：

```
定宽列：章 60 + 标题 160 + 时间跨度 130 + 状态 130 + 操作 220 = 700px
弹性列：目标 min-width 220 + 钩子 min-width 200            = 420px
声明列宽合计 = 1120px    ←→    容器 style="max-width: 980px"
```

后果三连（同一根因）：① 列被压扁，`时间跨度` 名义 130px 实际约 40px，表头**竖排成 4 行**；② 末列「操作」被裁在表格右边缘；③ 1920 窗口下约 **43% 宽度全空**。这不是「留白不好看」，是宽度上限与列宽声明打架——**本方案据此把「表格宽度口径」升格为跨阶段的全站规则**（见第三节）。

## 三、宽度口径：按比例，不设 px 上限（全站规则，P2 落地）

这条独立成节，是因为它跨所有页面、且优先级高于其余样式工作——它决定「页面看起来正不正常」。

**核心原则：宽度按容器比例分配，禁止裸 px 上限。** 本方案初稿曾提议把逐页 `max-width` 收成一个全局 `--ng-content-max: 1680px`——那只是把 18 个魔法值合并成 1 个魔法值，病根没除。正确做法是让宽度由容器比例决定。

**规则**：

1. **表格一律 `width: 100%`**，占满内容区，不设任何 px 上限——窗口多宽，表格多宽。彻底删掉逐页 `max-width`（清单见附录 B）。
2. **多余宽度按比例分给弹性列**：定宽列只用在真正定宽处（章号/状态/操作），其余列一律 `min-width`，由 Element Plus 按比例分配剩余宽度。窗口变宽时是**内容列变宽**，不是表格变宽。
3. **禁止「声明列宽合计 > 容器宽度」**：这是 `PlanningView.vue:52` 那个缺陷的根因，P2 逐表核销。
4. **表头不竖排**：表头 `white-space: nowrap` 并给列宽下限，杜绝 `时间跨度` 这类四字表头折成 4 行。
5. **确需上限时用比例或字号相对单位，不用 px**：优先 `min(100%, Nvw)`；与字号相关的用 `rem`/`em`/`ch`（随用户字号缩放）。若某处确实需要 px 硬上限，必须在附录 B 登记并写明理由（如 `LoginView.vue` 的登录卡 360px）。
6. **长文正文的上限用「全角字数」表达**（P5 阅读面）：`46em` 这类随字号缩放的版心，而不是 px——用户调大字号时版心同步变宽，每行仍是同样的字数。

**执行顺序**：先做 P2 的表格宽度（改动小、收益立刻可见、可独立回退），再让 P3 的 `DataTable` 组件把这条规则固化下来，避免全站表格被改两遍。

#### P3 补记（commit 7）：上一轮的遗漏与补抽

P3 是按「重复度从高到低」排的，但**漏了比页头重复更多的一类**：说明文字（51 处）远比页头（5 处）多，只因它在各页有三种写法变体（`font-size:var(--text-xs);color:var(--muted)` / 反序 / 无空格）才没被当成单一模式处理。这是判断疏漏，不是取舍。

**补抽结果**：

| 项 | 处理 | 说明 |
|---|---|---|
| `SceneStream.vue` | 新增组件 | 工作台里这段写了**三遍**（`scenes` 循环、会话转录的 `scene` 分支、`pstream` 分支又抄一份「收起思考」），流式三态标签/复用完成标签/思考折叠链接/占位文案/think 块全部逐字重复。工作台 1132→1098 行 |
| `.hint` | 工具类，110 处 | 说明文字 |
| `.cell-empty` | 工具类，18 处 | 空值占位「-」「—」 |
| `.toolbar` | 工具类，23 处 | 工具栏行；`gap` 原为 10/14px 两种，统一收到 4px 栅格上的 `--space-3`(12px) |

**为什么这三组用工具类而不是组件**：它们是纯样式、无行为，做成组件是过度抽象。

**实测效果**：全站重复度 **45 组 / 324 处 → 34 组 / 253 处**。剩余大头恰好是两类「不该做成组件、该走令牌」的：`margin-bottom` 间距（41 处）与表单控件 `width`（17 处，另有 100/130/140/160/180/200/220/230/260px 等，合计 64 处逐处手写）。

> **表单控件宽度是与 P2 表格 `max-width` 同类的魔法值问题**——P2 只修了表格，没注意到输入框/下拉框的宽度也是逐处手写。需先定几档宽度令牌，属设计决策，并入 P5 一起做。

**批量替换的第二次教训**：`utilize-inline-style.py` 自身出了两个 bug——①插入 `class` 时漏前导空格，产出 `<spanclass=`（构建报 `Invalid end tag`）；②声明比较未归一化冒号后的空格，`font-size: var(--text-xs)` 未被识别为应移除项，留下残余 style。**修法是回滚 `web/src` 后重跑修好的脚本，而不是打补丁**——同类机械改动出问题时，回滚重做比就地修补可靠。另有一条约束值得记：收空白噪音时，`空格+>` 这种朴素规则**不能全文件套用**，因为 `v-if="it.attempt > 1"` 的 `>` 在属性值内部，会被改成 `>1` 而改变语义；最终规则限定为「引号后跟属性名或 `>`」并逐处抽验。

### P4 归并散落的灰阶与字号为语义令牌（已执行，2026-10-03，commit 6）

**结果**：304 处硬编码颜色 + 241 处 px 字号 → 令牌引用，涉及 15 个文件。完整映射表见 **附录 A**。

**这一批修掉的是可量化的可访问性缺陷**：换掉的 11 种灰 + 5 种语义色里，除 `#606266` 与 `#c45656` 外**全部不达 WCAG AA**（`#999` 2.70、`#bbb` 1.74、`#e6a23c` 2.08、`#67c23a` 2.13、`#409eff` 2.64）。换令牌后最低为 `--meta` 的 4.9:1。

### P5 正文阅读面（已执行，2026-10-03，commit 8）

旧实现是弹窗里一段写死的 `white-space: pre-wrap` + 720px 版心 + 硬编码衬线 + `--text-lg`，无控制、无缩进、无持久化。

**产出两个文件**：

- `web/src/readingSettings.js` —— 阅读偏好（字号/行高/版心/字体/底色）的 **reactive 单例 + localStorage 持久化**。抽成独立模块而非塞进组件，是因为会话视图的正文块也要吃同一份偏好——共享单例即可，不必逐层传 props。坏 JSON / 缺字段 / 越界值一律回退默认，不让一份坏数据把阅读面卡死。
- `web/src/components/ReadingPane.vue` —— 阅读面本体。

**五个可调维度**：字号 16/17/18/20/22 · 行高 1.6/1.8/2.0/2.2 · 版心 32/38/46/52 全角字 · 字体 宋/黑 · 底色 浅/护眼/深。

**三处关键实现**：

1. **版心按「全角字数」表达并渲染为 `em`**：1em ≈ 1 全角字，46em ≈ 每行 46 字；用户调大字号时版心同步变宽、每行字数不变。这是第三节规则 6 的落地——按比例，不是设 px 上限。
2. **中文排版惯例**：段首 `text-indent: 2em`；段间距（`margin-bottom: 1em`）与行高分离，各行内密度、段管块感。这两项此前完全没有，是长文阅读体验的最大短板。正文按换行切段渲染成 `<p>`（而不是一个 pre-wrap 大块），并剥掉原有的行首空白避免双重缩进。
3. **三种底色只换一层局部变量**（`.rp--light/sepia/dark` 重绑 `--rp-bg/--rp-fg/--rp-border`），排版规则不变。深色不是把浅色反相，是另给一套暖色值（`#141413` / `#e8e6dd`）。

**会话视图同步**：`SceneStream` 的正文块经共享的 `readingSettings` 取字号与行高（版心不管——会话视图有自己的 880px 容器）。

## 六、验证策略（本方案的关键约束）

**本项目的视觉走查有两道独立障碍**：用户全局规则禁用可见浏览器面板，且本机 `agent.browsers.list()` 只返回 `iab` 一个后端（无 headless 可用）。因此**本方案不承诺视觉走查**，改用替代证据顶住，并显式列出未覆盖面。

替代证据五件套（每个阶段收尾执行）：

1. **dev 转译** `npm run dev` 通过（用户实际入口是 dev server，不是 `dist`）
2. **生产构建** `npm run build` 通过（抓模板语法/引用错误，可查新组件是否独立成 chunk）
3. **字段契约核对**：模板真正读到的字段与接口返回做双向差集（本批不改接口，预期差集为空——作为「没改坏」的证伪）

5. **接口实弹**：后端 8090 起，登录后跑一遍涉及页面的读接口

**必须显式声明的未覆盖面**（对人眼才可见的，直接请用户点）：

- 视觉观感（颜色/间距/宽度是否真的更好看）
- 动效过渡是否自然
- 阅读面的字号/行高切换手感
- 拖拽手势（本轮不涉及）

**用户目检检查点（3 处，不可省）**：

### P2 执行结果（2026-10-03，commit 4）

清理了 **18 张表的 `max-width`** 与 **4 处非表格容器**的上限。

**执行中发现的一条源码级事实（比 max-width 更根本）**：读 `element-plus/es/components/table/src/table-layout.mjs` 的 `updateColumnsWidth()`——

```js
const flexColumns = flattenColumns.filter((column) => !isNumber(column.width))
if (flexColumns.length > 0 && fit) { /* 把剩余宽度按 minWidth 比例分给弹性列 */ }
else { /* realWidth = width || minWidth；表格宽度 = 各列之和，不拉伸 */ }
```

即 **el-table 只在「存在弹性列（列上没有数字 width）」时才分配剩余宽度**。一个全列定宽的表，即使删掉 `max-width` 也照样按各列之和渲染，右侧仍留空——**光删上限治不了这类表**。

因此额外把 4 张全列定宽表中的描述列改成 `min-width`，使其成为弹性列（并把该检查脚本化：正则须写 `<el-table(?![-\w])`，否则 `<el-table\b` 会连 `<el-table-column` 一起匹配，我第一版就因此把 237 个列误报成表）：

| 表 | 原渲染宽度 | 处理 |
|---|---|---|
| `ChaptersView.vue:70` 门禁检查表 | 580px | 指标列改 `min-width` |
| `LibraryView.vue:72` 正典文档 | 440px | 名称列改 `min-width` |
| `LibraryView.vue:412` 指纹基线 | 520px | 指标列改 `min-width` |
| `LogsView.vue:32` 调用台账（11 列） | 1100px | 节点与模型列改 `min-width` |

**收尾核验**：全站 37 张表，**0 张全列定宽**；表格 `max-width` 残留 0；`npm run build` 通过。

**已知观感风险**：`LogsView` 的调用台账是 11 个窄列均质表，拉满到 1720px 后「节点/模型」两列会明显偏宽（节点名最长约 18 字符）。这是「按比例铺满」规则在均质窄列表上的固有代价，取舍留给人工检查点 B 判断。

## 附录 C：设计系统来源与产出（2026-10-03）

### 工具

用 [OpenDesign](https://github.com/nexu-io/open-design)（Apache-2.0，开源版 Claude Design 替代品）出设计。它不自带 agent——PATH 上的 coding agent 才是设计引擎；它提供的是可移植的 design systems / skills / templates / plugins 四类资产。本机安装于 `D:\Program\open-design`（只装了 design-systems 目录 + 契约 + 取用脚本，全量 277MB 未取；原因与本机 GitHub 通道说明见该目录 `INSTALL-NOTES.md`）。

### 基座选择

153 个设计系统里选 **`kami`（紙 / 纸，Editorial & Print）**作基座，理由：

1. 它是目录里唯一**从设计之初就为 zh-CN 排版**做的系统（带 TsangerJinKai02 / 思源宋体中文衬线栈，且明写支持 EN · zh-CN · ja）；
2. 印刷节奏（行高 1.45–1.55、标签用实色 hex、数字 `tabular-nums`）与数据表密度天然接近；
3. 暖羊皮纸底 + 墨蓝单一彩色，比 `claude`（赭石，偏消费向）更贴合「专业写作工具」而非「聊天产品」。

对照过 `claude`（暖羊皮纸/赭石/文学化）与 `linear-app`（暗色优先/高密度），二者未采用。

| # | 改造 | 原因 |
|---|---|---|
| A | **密度** | kami 面向印刷单页（section 72px、container 1120px）；本系统面向数据密集运维台，压缩纵向节奏，且 `--container-max` 置为 `100%`（= 不设上限，落实第三节的按比例口径） |
| B | **重设状态色**（硬需求） | kami 自述「面向印刷，几乎不需要状态色」，其暖色语义在 0.14 alpha 底上 warn 仅 3.82:1 且五族底挤成一片暖灰；本平台状态标签是主要信息载体，故重设五族实色三元组，全部实算过 AA |
| C | **阅读面** | 中文长文需要比印刷文档更大的行高与**段首缩进**，新增 `--reading-*` C-extension（含 `--reading-measure: 46em`，按字号缩放而非 px） |
