## 1. 目标与非目标

**目标（一句话）**：把业务侧从「模式中心制」（`derive_config.mode` 字符串比较散落各处）重建为「配方中心制」——**一个深 module：配方（interface）+ 能力声明与解析（implementation）**，消费方只问「这本书被授予了什么能力」，不再知道 mode 的存在。

**目标（可验收）**：

1. 全库对 `mode` 的散落字符串比较**引用清零**（grep 只剩配方入口归一一处）；
2. 同一谓词在 seam 上的重复实现（现状 7 处，见 §2）收敛为**单读口**；
3. SPLICE 接入 = 能力表**加一行** + `TaskKind.SPLICE` + 四步链，不新增任何 mode 分支；
4. 不验收「旧行为保持不变」——验收新链路行为符合本文能力表（§3.2）。

**非目标（YAGNI，本轮明确不做）**：

- 执行管线内部（场景→门禁→digest）与 `GateService` 判定实现——不是本次 seam；
- 校验层「统一 Verdict / 处置表驱动」——已挂起，等第二个真实调用方；
- RESKIN **功能**删除——能力行保留，只重接实现；
- 词条体系落地——`gates` 段只留字段与接口位，判据分发表属校验层另文档；
- 前端框架改造——向导配方卡是模板重写，不是组件库换血。

## 2. 现状诊断（事实基线）

### 2.1 同一谓词在 seam 上重复实现 7 次，且已三处漂移

`migrate()`（`DeriveSupport.java:33-35`，语义＝**MIGRATE‖RESKIN**）的消费点：

| # | 位置 | 判据形式 |
|---|---|---|
| 1 | `ChapterPipelineService:159` 自愈不换目标 | `isMigrate`→`migrate()` |
| 2 | `ChapterPipelineService:1067` 审校档2 replan 禁令 | `cfg.migrate()` |
| 3 | `GenerationQueueService:181,200-211` 入队口拒卷规划 | `migrate()` |
| 4 | `VolumePlanService:426,434-438` adopt 兜底 | `migrate()` |
| 5 | `NovelService:186-190` activate 骨架放行 | `migrate()` |
| 6 | `NovelService:639-640,668-671,707-711` 克隆分流 | **手写 `MIGRATE‖RESKIN` 字符串比较**（未走 `migrate()`） |
| 7 | `NovelService:1069-1071,1089-1096` 复刻审校三值分流 | 双比较 + DB 回落 |
| — | `WizardView.vue:137-159,357` 前端条件表单 | computed **复刻**了后端 `migrate()` 语义 |

**已实证的漂移三处**（重复实现的必然代价）：`ChapterPipelineService:1130` 注释写「=MIGRATE」实为双值；`NovelService:682` 日志把换皮书记成 `"MIGRATE"`；`GenerationQueueService:207-208` 对 RESKIN 书弹「剧情迁移」文案。

另有互斥的提示词注入 seam：`ContextPackerService:78-86`（`migrate()`→`derive_migrate`，否则 `derive_redline`）。

### 2.2 deletion test：能力表若只是换写法＝搬家

删除散落判据、换成 `profile.can(X)`——**如果 9 个 if 变成 9 次 `can()` 调用，分支数不变，那是搬家不是收敛**（codebase-design 的删除测试不过）。真正收敛必须做到两点：

1. **蓝图守卫按结构事实收敛**。摸底发现现成的正例：`ChapterPipelineService.outlineStep:675` 的「场景已物化 → DONE」是**结构判据**，完全不读 mode 却承担了「迁移/换皮章不许重编」的核心语义。守卫 1/2/3/4（§2.1）应全部改问同一个结构事实——「本章是否存在受保护蓝图（outline_yaml / chapter_scenes 非空）」——而不是问 mode。**mode 能力表只保留真正模式相关的决定**：克隆什么、注入哪段提示词、进哪个任务队列、跑不跑复刻审校。
2. **克隆/激活/审校/注入四类由同一读口驱动**。现在克隆走手写比较、激活走 `migrate()`、入队走 `normalizeMode==RESKIN`（`NovelController:103-111`）——三套读法必须并成一个 adapter。

### 2.3 其他事实

- **`Cfg` record 12 字段**（`DeriveSupport.java:23-26`），另有约 15 处**非 mode** 的 `Cfg` 消费方（`VolumePlanService:130`、`GateService:141`、`ContextPackerService:58,98` 等）——配方重构**不得误伤**这些读口（`water/pov/targetChapters…` 的读取路径行为不变，只是载体换段）。
- **数据面**：`novels.derive_config` JSONB，唯一 UPDATE 在 `NovelMapper.xml:46`；Flyway 无 mode 迁移（`V26` 只建列）。**库内分布（psql 已验证）：mode 缺失 17、`RESKIN` 6、`MIGRATE` 2、显式 `ORIGINAL` 0——存量只需处置 8 行显式值。**
- **模块分布**：mode 判据 100% 在 `novelgen-service` + `novelgen-app` 入队口 1 处 + `novelgen-model` 的 DTO/TaskKind + `novelgen-llm` 的模板常量；`novelgen-data` 零判据（只存 JSONB）——**新能力表放 service 层不破坏 §1.1 依赖方向**。
- **RESKIN 的「专属」比想象少**：`ReskinService.run` 自身不判 mode（只校验 `sourceSampleId` 与样本章级节点），mode 相关只有入队口判据 + `cloneSampleAssets` 的 `!reskin` 分支——重接面小。

## 3. 目标架构

### 3.1 分层总览

```
消费方（守卫/克隆/激活/注入/入队/审校/向导）
   │  只问两件事：① 结构事实 ② profile 能力
   ├──► 结构判据：blueprintProtected(novelId, chapterNo)   ← 纯读库，无 mode
   └──► DeriveProfile（深 module，见 3.2）
              ▲
   Recipe（derive_config 结构化四段 + preset 入口）
```

**关键设计决策：守卫归属（2026-10-08 实施前修正——原「守卫纯结构化」方案被代码核实推翻）。**

- **结构判据只保留它已经成立的地方**：`outlineStep:675`「场景存在 → 跳过章纲步」原样不动（本就 mode-free）。但**不能**把 §2.1 守卫 1-4 改成纯结构判据——反例已核实：ORIGINAL 书的自愈梯子（`chapter_replan` 换目标）与卷规划 adopt 对未生成章的覆盖是**正常功能**，而这些章的 `outline_yaml`/`chapter_scenes` 同样非空；按「蓝图存在」一刀切会误杀自愈与规划。「章纲是外部素材还是系统自产」在库里**没有结构事实可依**（无来源标记列），只能由配方携带。
- **能力守卫（进能力表）**：守卫 1-4 收敛为 `PROTECT_BLUEPRINT`（replan 早退、审校档 replan 禁令）与 `FORBID_VOLUME_PLAN`（入队口/adopt 拒绝）两个能力，读口唯一（`DeriveProfile`）——**deletion test 的收敛来自谓词从 7 处重复实现并成 1 处读口，而不是把谓词消灭掉**；真正的深化点是克隆/激活/审校/注入/入队五类由同一读口驱动。

### 3.2 深 module：`DeriveProfile`

- **interface（调用方必须知道的全部）**：
  - `Recipe`（配方）：`sources`（单样本/多本书/纯原创）+ `clones`（资产勾选）+ `tags`/`gates`（词条两族位）+ `params`（现 12 字段收编）+ `preset`（入口标记 ORIGINAL/RESKIN/SPLICE，`MIGRATE` 移除）；
  - `Profile`（能力查询）：`can(Capability)` 与少量语义化读口（见下），**不变量在 interface 上**：非法配方（如 SPLICE 不带 ≥2 个 `sources`）在解析时即拒绝，fail-open 只对「preset 缺失 → ORIGINAL」保留（沿用 `normalizeMode` 的安全方向）。
- **implementation（藏起来的复杂度）**：能力表（preset → Capability 集）+ 配方归一化 + 不变量校验 + 存量数据解释。
- **Capability 枚举（初版，按目标态定义，不以现行行为为准）**：

  | Capability | ORIGINAL | RESKIN | SPLICE |
  |---|---|---|---|
  | `PROTECT_BLUEPRINT`（replan 早退 + 审校档 replan 禁令） | ✗ | ✓ | ✓ |
  | `FORBID_VOLUME_PLAN`（入队口 + adopt 拒绝覆盖） | ✗ | ✓ | ✓ |
  | `CLONE_ASSETS`（按 `clones` 段） | ✓ | ✗ | ✗（按 `sources` 取样） |
  | `RUN_ORIGINALITY_REVIEW` | ✓ | ✗ | ✗（改跑拼接审校） |
  | `INJECT_DERIVE_PROMPT`（提示词分流） | redline 段 | 蓝图口径段 | 蓝图口径段（拼接段后补） |
  | `QUEUE_BOOK_TASK`（建书入队） | ✗ | `TaskKind.RESKIN` | `TaskKind.SPLICE` |
  | `SEED_PRELUDE`（前情种子） | ✗（管线自然产生） | 换皮设定落 canon | **必须** |

- **为什么它深**：调用方学一个 `can(Capability)` / 一次 `blueprintProtected()` 就能驱动克隆、注入、入队、审校四类行为；换模式＝换表行，调用方零改动（leverage）。复杂度集中在校验与归一里，而不是散在 9 个 if 里（locality）。**adapter 只有一个（能力表）＝当前假想接缝？不是**——`Capability` 的每个取值就是一个已知会变的维度，且 SPLICE 行已在路上，接缝两侧的变化是确定的。

## 4. 接口草图（设计一次，实施前可再翻一版）

```java
// 语义位置：novelgen-service，DeriveSupport 同包邻接（§1.1：service 根包不细分）
public record Recipe(Sources sources, Clones clones, Tags tags, Gates gates,
                     Params params, Preset preset) {
    /** 解析 derive_config JSONB；不变量违例抛 PARAM_ERROR，preset 缺失 fail-open 到 ORIGINAL */
    public static Recipe parse(String json) { … }
}
public enum Preset { ORIGINAL, RESKIN, SPLICE }          // MIGRATE 不在其中
public enum Capability { CLONE_ASSETS, RUN_ORIGINALITY_REVIEW,
                         INJECT_DERIVE_PROMPT, QUEUE_BOOK_TASK, SEED_PRELUDE }
public final class DeriveProfile {
    public static Set<Capability> of(Recipe r);            // 能力表唯一读口
    public static <T> T dispatch(Recipe r, Capability c, …) // 需要带参分派的（队列类型/提示词段名）
}
// 结构守卫仅存于既有 mode-free 处（outlineStep 场景跳过），不新增 blueprintProtected 读口——
// 见 §3.1 修正：「章纲是外部素材」无结构事实可依，守卫走能力表。
```

**现存调用方改法对照**（摸底表 → 目标读法）：

| 现状 | 目标 |
|---|---|
| 守卫 1/2/3/4（`migrate()` 四连） | `can(PROTECT_BLUEPRINT)` / `can(FORBID_VOLUME_PLAN)`（§3.1 修正后口径） |
| 克隆手写双比较（`NovelService:639-`） | `DeriveProfile.of(recipe).can(CLONE_ASSETS)` + `clones` 段 |
| activate 骨架放行（`NovelService:186-`） | 结构判据（大纲是否仍为样本骨架原文）× 预设允许（ORIGINAL 才拒）——读口仍唯一 |
| 提示词注入（`ContextPackerService:78-86`） | `can(INJECT_DERIVE_PROMPT)` → 段名分派 |
| 入队口（`NovelController:104`） | `can(QUEUE_BOOK_TASK)` → `TaskKind` 分派 |
| 复刻审校三值分流（`NovelService:1069-`） | `can(RUN_ORIGINALITY_REVIEW)` |
| 前端 computed（`WizardView:357`） | 删除——表单按配方卡声明渲染，语义不再前后端双写 |

## 5. 存量数据迁移

**规模极小（psql 已验证）**：mode 缺失 17 行、`RESKIN` 6、`MIGRATE` 2、显式 `ORIGINAL` 0。无 Flyway mode 迁移历史，`V26` 只建列。

| 存量 | 处置 | 说明 |
|---|---|---|
| 缺失 17 行 | 读侧归一为 `preset=ORIGINAL` | 沿用 fail-open 方向，**可不写回库**（解析处归一，非双读——双读指新旧两套结构并存解释，这里只有一个新结构） |
| `RESKIN` 6 行 | 一次性迁为 `preset=RESKIN` 配方（`sources`=单样本） | 语义无损 |
| `MIGRATE` 2 行 | **开放决策 D1（见 §9）** | 关键事实：这两本的保护早已是结构性的（场景已物化 → `blueprintProtected` 自然成立），mode 值本身已无行为意义 |

- **不建双读、不留 legacy 键解释分支**（推翻重构姿态）；迁移用一个 Flyway 脚本（下一个号，改前先核 `flyway_schema_history`）或建书侧一次性修正——倾向 **Flyway 一次改完**，因为量小且要可审计。
- **`derive_config` 不是 schema 变更**，JSONB 加 `sources/clones/gates` 段、`mode`→`preset` 改名全在脚本/写侧完成；`params` 现有 12 字段原样平移。

## 8. 风险与缓解

| 风险 | 缓解 |
|---|---|
| **前端语义双写漂移**（摸底已证 computed 复刻后端语义） | M3 整段重写配方卡，**删除**而非修补 computed；前后端不再共享语义，只共享配方字段契约 |
| **RESKIN 重接打断在跑验证书** | 结构守卫（蓝图保护）不受 mode 移除影响，生成中书的保护天然延续；入队口能力读口在 M2 内一次切对，不留窗口 |
| **`Cfg` 15 处非 mode 消费方被误伤** | M0-M2 只动 mode 判据与写侧结构，`params` 字段名与读取路径不变；`mvn test` + 现有 `DeriveSupportTest` fail-open 用例兜底 |
| **PromptCatalog 改动需重启生效** | M2 涉及注入段名时按规约重启验证；`ReskinPromptArityTest` 防 fail-open 静默回退 |
| **Flyway checksum** | 迁移是新文件不动历史；若碰历史文件按 AGENTS 标准做法改 `flyway_schema_history.checksum` |
