# 业务侧推翻重构，而不是兼容式收编

2026-10-08。阶段二（SPLICE）开工前，业务侧 `derive_config.mode` 的处置有两条路：**兼容式收编**（能力声明表按现行行为逐格核销、消费方逐处替换读表、保留 `normalizeMode` 等旧行为、新旧双轨过渡）与**推翻重构**（配方结构化 + 能力表按目标态新建，旧 mode 分支是障碍清单、随切换整体拆除，不验收旧行为保持不变）。用户拍板选后者，原话：「我要的是推翻重构，现有代码逻辑只会影响阶段二功能的实现」。

**考虑过的方案**：兼容式收编——它通过全部现有测试的代价是把 9 个散落 if 换成 9 次 `can()` 调用（deletion test 不过，搬家而已），且 SPLICE 接入要在旧分支上再加特判，等于先造债再还。

**后果**：①验收口径变为「mode 散落比较引用清零 + 新链路行为符合能力表」，不保留旧行为；②存量 2 本 MIGRATE 书随 D1 修正归档为 RESKIN 能力集（其保护语义与换皮产线一致，详见重构规划 §9）；③RESKIN 功能保留但实现重接，验证书不构成保留旧实现的理由。
